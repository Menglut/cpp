# CppStudy 기술 정책 결정서

> 문서 상태: 구현 기준 확정  
> 결정일: 2026-09-28  
> 적용 범위: MVP 백엔드, 인증, 콘텐츠 관리, 코드 실행 및 자동채점  
> 관련 문서: `docs/gptMaking.md`, `docs/verification.md`

## 1. 문서 목적

이 문서는 `gptMaking.md`의 미정 기술 항목을 실제 구현에 사용할 기본 정책으로 확정한다. 이후 구현은 이 문서를 기준으로 진행한다. 정책을 변경할 때는 코드만 수정하지 않고 이 문서의 결정 내용과 변경 이력도 함께 갱신한다.

현재 저장소의 프런트엔드는 사용자 흐름을 검증하기 위한 프로토타입이다. 브라우저 `localStorage`에 저장되는 데모 로그인, 모의 실행, 모의 제출 및 관리자 초안은 이 문서에서 정의한 서버 기능으로 교체한다.

## 3. 선택 이유

### 3.1 NestJS를 사용한다

인증, 권한 가드, DTO 검증, 관리자 API, 비동기 제출 등 서버 책임이 많으므로 구조가 명시적인 NestJS를 사용한다. Express API를 별도로 추가하지 않는다. NestJS의 기본 HTTP 어댑터를 사용하고, 성능상 필요가 확인되기 전에는 어댑터 교체를 하지 않는다.

### 3.2 서버 세션을 사용한다

브라우저 서비스이며 웹과 API를 같은 사이트에서 제공하므로 JWT를 브라우저 저장소에 보관하지 않는다. 예측 불가능한 세션 ID만 쿠키로 전달하고 세션 원본 데이터는 서버에 저장한다. 로그아웃, 비밀번호 변경, 관리자에 의한 계정 정지 시 세션을 즉시 폐기할 수 있어야 한다.

### 3.3 Judge0를 실행 어댑터로 사용한다

MVP에서 자체 샌드박스를 처음부터 구현하면 실행 격리와 자원 계측 위험이 크다. 초기에는 자체 호스팅 Judge0 CE를 사용하되, 문제 관리·테스트 순회·출력 비교·최종 판정·기록은 CppStudy Worker가 담당한다.

Judge0 전용 호스트는 공개 인터넷에 API를 노출하지 않는다. CppStudy Worker만 사설 네트워크에서 접근한다. 향후 다른 실행 서비스로 교체할 수 있도록 `ExecutionProvider` 인터페이스 뒤에 둔다.

### 3.4 npm workspaces를 사용한다

현재 프런트엔드가 npm과 `package-lock.json`을 사용하므로 패키지 관리자를 추가로 도입하지 않는다. 루트에 단일 lockfile을 두고 Web, API, Worker, 공유 패키지를 npm workspaces로 관리한다.

## 4. 목표 시스템 구조

```text
브라우저
   │ HTTPS
   ▼
Nginx 또는 관리형 진입점
   ├── Next.js Web
   └── NestJS API ───── PostgreSQL
            │              └── Outbox
            └────────── Redis / BullMQ
                              │
                        Judge Worker
                              │ 사설 네트워크
                              ▼
                    자체 호스팅 Judge0 CE
                    전용 Linux 실행 호스트
```

- 브라우저는 PostgreSQL, Redis, Worker 및 Judge0에 직접 접근하지 않는다.
- Web과 API는 동일 사이트에서 서비스한다. 운영 환경에서 임의 Origin의 CORS 요청은 허용하지 않는다.
- API는 제출을 직접 실행하지 않고 DB에 제출과 Outbox 이벤트를 한 트랜잭션으로 저장한다.
- 큐 메시지에는 제출 ID나 실행 ID만 넣고 소스 코드, 숨김 테스트, 비밀번호를 넣지 않는다.
- Worker는 DB에서 고정된 문제 버전과 실행 정보를 읽고 결과를 조건부로 저장한다.

## 5. 모노레포 정책

목표 구조는 다음과 같다.

```text
cpp-study/

│   ├── web/                 # 기존 frontend 이전 완료
│   ├── api/                 # NestJS REST API
│   └── judge-worker/        # BullMQ 소비 및 판정 조율
├── packages/
│   ├── contracts/           # 공개 요청·응답 스키마와 타입
│   ├── config/              # 공통 TypeScript·lint 설정
│   └── judge-domain/        # 판정 상태와 비교기 순수 로직
├── prisma/
│   ├── schema.prisma
│   ├── migrations/
│   └── seed.ts
├── tests/
│   ├── integration/
│   ├── e2e/
│   └── judge-fixtures/
├── docker/
├── docs/
├── package.json
```

- Prisma 내부 모델을 프런트엔드와 공유하지 않는다.
- `contracts`에는 공개 가능한 필드만 포함한다. 숨김 테스트와 기준 출력 타입은 브라우저 번들에 포함하지 않는다.
- 기존 프런트엔드는 `apps/web`으로 이전했으며 루트 workspace의 공통 명령으로 관리한다.

## 6. API 정책

### 6.1 기본 계약

- 기본 경로는 `/api/v1`이다.
- 요청과 응답은 JSON을 사용한다. 파일 업로드 기능은 MVP에 포함하지 않는다.
- 소유자와 role은 세션에서 결정한다. 클라이언트가 보낸 `userId`, `role`, 판정 및 자원 제한은 신뢰하지 않는다.
- 식별자는 내부적으로 UUID를 사용한다. 문제의 사용자 노출 번호는 별도 정수 컬럼으로 관리한다.
- 목록은 cursor 기반 페이지네이션을 사용한다. 기본 20개, 최대 100개다.
- 비동기 실행과 제출 생성은 `202 Accepted`와 자원 ID를 반환한다.
- 공식 제출에는 `Idempotency-Key`를 필수로 받는다. 같은 키와 같은 본문은 같은 제출을 반환하고, 본문이 다르면 `409`를 반환한다.
- API 문서는 OpenAPI로 생성하며 CI에서 계약 변경을 검사한다.

### 6.2 오류 형식

```json
{
  "error": {
    "code": "PROBLEM_VERSION_CONFLICT",
    "message": "문제가 갱신되었습니다. 새 버전을 확인해 주세요.",
    "requestId": "request-uuid"
  }
}
```

- 입력 오류 `400`, 미인증 `401`, 권한 없음 `403`, 미존재·비공개 `404`, 충돌 `409`, 크기 초과 `413`, 요청 제한 `429`를 사용한다.
- 운영 응답에 스택 트레이스, SQL 오류, 숨김 테스트, 비밀번호, 세션 ID를 포함하지 않는다.

### 6.3 결과 조회

- 실행과 제출 결과는 처음 1초 간격으로 조회하고 점차 늘려 최대 5초 간격으로 폴링한다.
- 최종 상태가 되면 폴링을 중단한다. 탭이 비활성 상태이면 빈도를 낮춘다.
- 네트워크 오류나 응답 지연을 WA 또는 SYSTEM_ERROR로 추정하지 않는다.
- SSE/WebSocket은 MVP 안정화 후 별도 결정한다.

## 7. 인증과 권한 정책

### 7.1 계정과 비밀번호

- 이메일은 소문자로 정규화해 고유하게 관리한다.
- 비밀번호는 Argon2id로 해시하며 평문이나 복호화 가능한 형태로 저장하지 않는다.
- 구체적인 Argon2 비용 값은 배포 서버에서 약 100~250ms의 검증 시간이 나오도록 벤치마크 후 고정한다.
- 공개 회원가입으로 생성할 수 있는 role은 `USER`뿐이다. `ADMIN`은 운영 절차나 seed를 통해서만 부여한다.
- 이메일 인증과 비밀번호 재설정 메일은 초기 비공개 MVP에서 제외하고 공개 출시 전에 별도 정책을 확정한다.

### 7.2 세션

- 쿠키 이름은 `cppstudy_session`으로 한다.
- 쿠키는 `HttpOnly`, 운영 환경 `Secure`, `SameSite=Lax`, `Path=/`를 적용한다.
- 쿠키에는 256비트 이상의 임의 세션 토큰만 저장한다.
- DB에는 세션 토큰 원문이 아닌 해시, 사용자 ID, 생성·만료·마지막 사용 시각을 저장한다.
- 로그인 성공 시 세션 ID를 새로 발급한다. 로그아웃과 비밀번호 변경 시 관련 세션을 폐기한다.
- 초기 정책은 유휴 만료 24시간, 절대 만료 7일이다. 자동 연장은 절대 만료를 넘지 않는다.
- 서버 메모리 세션 저장소는 개발 환경에서도 사용하지 않는다.

### 7.3 CSRF와 요청 제한

- 상태 변경 요청은 `Origin`/`Host`를 검증한다.
- 세션 쿠키와 별도로 CSRF 토큰을 사용하고 변경 요청 헤더에서 검증한다.
- 로그인은 IP와 계정 키를 조합해 제한한다. 초기값은 IP당 10회/10분, 계정당 5회/10분이다.
- 코드 실행과 제출은 사용자당 동시 2개로 제한한다.
- 실제 제한 값은 부하 시험 후 조정하되 제한 기능 자체는 MVP 필수다.

### 7.4 접근 제어

- 제출 소스, 실행 입력·출력 및 개인 학습 데이터는 소유자와 관리자만 접근한다.
- 숨김 테스트 입력과 기대 출력은 관리자 전용 API에서도 필요한 화면에만 제한적으로 반환한다.
- 관리자 UI 표시 여부와 무관하게 모든 `/admin` API에서 서버 권한을 검사한다.
- 계정 ID나 제출 ID만 변경해 다른 사용자의 데이터를 조회할 수 없는지 통합 테스트를 둔다.

## 8. 데이터 정책

- PostgreSQL이 사용자, 콘텐츠, 문제 버전, 제출 및 판정의 원본 저장소다.
- Prisma migration 파일을 코드와 함께 커밋하며 운영 DB에 `db push`를 사용하지 않는다.
- 모든 서버 시각은 UTC `timestamptz`로 저장한다.
- 화면 표기와 학습일 경계는 `Asia/Seoul`을 기본으로 한다.
- 공개 문제의 테스트, 제한 또는 판정 정책을 변경하면 기존 버전을 수정하지 않고 새 `problem_version`을 만든다.
- 공식 제출은 제출 당시 `problem_version`, 소스, 언어, 컴파일 환경과 연결한다.
- 사용자 판정이 완료된 공식 제출은 수정하지 않는다. 재채점 결과가 필요하면 별도 판정 이력을 추가한다.
- 문제와 강의 삭제는 기본적으로 보관 처리한다. 과거 제출이 참조하는 버전은 물리 삭제하지 않는다.

## 9. 큐와 장애 복구 정책

- Redis + BullMQ를 사용하며 실행과 공식 제출 큐를 분리한다.
- API는 제출/실행 레코드와 Outbox 이벤트를 한 DB 트랜잭션으로 저장한다.
- Dispatcher가 미전달 Outbox를 Redis에 등록하고 전달 시각을 기록한다.
- 큐는 최소 한 번 전달을 전제로 하며 Worker는 중복 실행에 안전해야 한다.
- 작업 키는 `submissionId` 또는 `runId`를 포함한다.
- Worker는 임대와 `attemptNo`를 확보한다. 현재 시도 번호와 일치하는 Worker만 결과를 확정할 수 있다.
- AC, WA, CE 같은 사용자 판정은 자동 재시도하지 않는다.
- 인프라 오류만 최대 2회 재시도하고 초과하면 `SYSTEM_ERROR`로 확정한다.
- 최종 상태가 있는 제출은 일반 큐 소비 과정에서 다시 실행하지 않는다.
- 큐 메시지와 애플리케이션 로그에 전체 소스와 테스트 데이터를 기록하지 않는다.

## 10. C++ 실행과 자동채점 정책

### 10.1 지원 환경

- MVP 언어 식별자는 `CPP17` 하나만 제공한다.
- GCC/G++ 고정 버전을 사용하고 배포 이미지 digest를 기록한다.
- 최초 구현 기준 컴파일 옵션은 `-std=c++17 -O2 -pipe`다.
- `-Wall -Wextra` 경고는 관리자 검증에서 확인할 수 있지만 경고를 컴파일 실패로 처리하지 않는다.
- Judge0의 숫자 언어 ID는 코드에 하드코딩하지 않고 배포 환경 설정으로 관리한다.
- 실제 GCC 버전과 Judge0 언어 ID는 실행 이미지 채택 시험 후 이 문서의 배포 기록에 추가한다.

### 10.2 실행 제공자 계약

Worker는 다음 의미의 `ExecutionProvider` 인터페이스에만 의존한다.

```ts
type ExecutionRequest = {
  language: "CPP17";
  sourceCode: string;
  stdin: string;
  compileLimit: ResourceLimit;
  runLimit: ResourceLimit;
};

type ExecutionResult = {
  status: "SUCCESS" | "CE" | "RE" | "TLE" | "MLE" | "OLE" | "SYSTEM_ERROR";
  stdout?: string;
  stderr?: string;
  compileOutput?: string;
  executionTimeMs?: number;
  memoryUsageKiB?: number;
  providerRequestId?: string;
};
```

- Provider의 정상 실행 상태를 곧바로 문제 AC로 간주하지 않는다.
- CppStudy Worker가 신뢰 영역에서 기대 출력과 실제 출력을 비교하고 최종 판정을 집계한다.
- 제공자가 명확한 근거를 주지 않는 판정은 추정하지 않고 `SYSTEM_ERROR`로 처리한다.
- 숨김 테스트의 stdout/stderr 원문은 학습자 응답에 반환하지 않는다.

### 10.3 출력 비교

기본 비교기는 `TOKEN`이다.

- TOKEN 비교는 ASCII 공백, 탭, 줄바꿈으로 토큰을 나누고 토큰 순서와 값을 정확히 비교한다.
- 선행·후행 공백과 연속 공백, 줄바꿈 차이는 무시한다.
- 빈 출력과 토큰 추가·누락은 WA다.
- 숫자 토큰도 문자열로 정확히 비교한다. 실수 오차 비교는 MVP에 포함하지 않는다.
- 출력 형식 자체가 문제 조건인 경우에만 문제 버전에 `EXACT`를 지정한다.
- EXACT는 줄 끝을 LF로 정규화한 뒤 바이트 수준으로 비교한다. 마지막 줄바꿈 허용 여부는 문제 버전에 명시한다.

### 10.4 판정 상태

- 접수 및 처리 상태: `PENDING`, `QUEUED`, `COMPILING`, `RUNNING`
- 사용자 코드 최종 판정: `AC`, `WA`, `CE`, `RE`, `TLE`, `MLE`, `OLE`
- 시스템 판정: `SYSTEM_ERROR`, `CANCELLED`
- 해결 상태는 유효한 공식 제출에서 AC가 한 번이라도 있는 경우 유지한다.
- PENDING, SYSTEM_ERROR, CANCELLED만 존재하는 문제는 실패 시도로 계산하지 않는다.

### 10.5 초기 자원 제한

| 항목 | 초기값 |
|---|---:|
| 소스 코드 | UTF-8 64 KiB |
| 직접 실행 stdin | UTF-8 64 KiB |
| 문제당 테스트 수 | 최대 50개 |
| 테스트 입력 | 개별 256 KiB |
| 컴파일 wall time | 10초 |
| 컴파일 메모리 | 512 MiB |
| 실행 CPU time | 테스트별 1초 |
| 실행 wall time | 테스트별 3초 |
| 실행 메모리 | 테스트별 128 MiB |
| stdout + stderr | 테스트별 총 1 MiB |
| 사용자 동시 실행·제출 | 합계 2개 |
| 인프라 오류 재시도 | 최대 2회 |

- 문제별 시간·메모리 제한은 관리자 정책 범위 안에서만 설정할 수 있다.
- 클라이언트가 전송한 제한값은 무시한다.
- 기준 코드와 알려진 판정 fixture로 측정한 뒤 공개 전에 수치를 재검증한다.

### 10.6 실행 격리

- Judge0는 Web/API와 다른 전용 Linux VM 또는 물리 호스트에서 실행한다.
- 전용 호스트의 관리 API는 공인 인터넷에 노출하지 않는다.
- 사용자 코드의 외부 인터넷, 내부망, 메타데이터 서버 접근을 차단한다.
- 비루트 실행, capabilities 최소화, `no-new-privileges`, 읽기 전용 기반 파일시스템과 제한된 임시 공간을 적용한다.
- Docker 소켓, DB/Redis 자격 증명, 전체 테스트 디렉터리를 실행 환경에 전달하지 않는다.
- 각 테스트는 파일·프로세스 상태가 공유되지 않는 깨끗한 환경에서 실행한다.
- 무한 루프, fork/process 폭주, 메모리 폭주, 파일·출력 폭주 및 네트워크 접근 차단 시험을 통과해야 공개할 수 있다.

## 11. 콘텐츠 정책

현재 프런트엔드의 다음 콘텐츠를 DB seed의 출발점으로 사용한다.

- 강의 6개: 시작과 입출력, 변수와 자료형, 조건문, 반복문, 배열과 문자열, STL 시작하기
- 문제 7개: Hello C++, 두 수 더하기, 홀수일까 짝수일까, 배열 뒤집기, 1부터 N까지의 합, 가장 큰 수 찾기, 작은 수부터 정렬

각 문제는 공개 전에 다음 기준을 만족해야 한다.

- 설명, 입력, 출력, 제약, 시간·메모리 제한이 있다.
- 공개 예제가 1개 이상 있고 예제 출력이 기준 코드 실행 결과와 일치한다.
- 경계값을 포함한 숨김 테스트가 3개 이상 있다.
- 기준 코드가 모든 테스트를 통과한다.
- 의도적으로 만든 WA, CE, RE, TLE, OLE 코드가 예상 판정을 받는다.
- 연결 강의와 추천 순서가 저장되어 있다.

강의와 문제의 Markdown은 원시 HTML과 MDX/JavaScript 실행을 허용하지 않는다.

| 데이터 | 초기 보관 정책 |

- 백업에도 같은 접근 통제와 만료 정책을 적용한다.

## 13. 개발·배포 환경

### 13.1 로컬 개발

- Web, API, PostgreSQL, Redis는 Docker Compose로 재현할 수 있게 한다.
- Judge0는 무거운 의존성이므로 별도 Compose profile 또는 별도 개발 호스트로 실행한다.
- Judge0가 없는 UI/API 개발을 위해 실제 판정을 가장하지 않는 명시적 fake provider를 제공할 수 있다.
- `.env.example`에는 변수 이름과 안전한 예시만 넣고 실제 비밀 값을 커밋하지 않는다.

### 13.2 운영

- Linux + HTTPS를 기준으로 한다.
- Web/API 호스트와 Judge0 실행 호스트를 분리한다.
- PostgreSQL과 Redis 관리 포트를 공인 인터넷에 공개하지 않는다.
- 이미지 태그만 사용하지 않고 digest를 기록한다.
- DB migration은 배포 단계에서 명시적으로 실행하고 실패 시 애플리케이션 전환을 중단한다.
- 진행 중인 작업은 Worker 임대 만료와 재시도 정책으로 복구한다.

클라우드 제공자, 도메인, 실제 VM 크기와 관리형 DB 사용 여부는 기능 구현을 막지 않는 인프라 선택이므로 배포 준비 단계에서 비용과 운영 조건을 비교해 확정한다.

## 14. 관측과 품질 기준

- 모든 API 응답과 로그를 `requestId`로 연결한다.
- 비동기 작업은 `submissionId` 또는 `runId`, `attemptNo`, provider request ID로 추적한다.
- 큐 대기 시간, 실행 시간, 판정별 수, SYSTEM_ERROR 비율, Worker 생존 상태, Outbox 지연을 측정한다.
- 비교기와 판정 집계는 단위 테스트를 작성한다.
- 인증, 권한, DB, Outbox 및 큐 중복 처리는 통합 테스트를 작성한다.
- 강의 → 문제 → 실행 → 제출 → 기록 조회는 E2E 테스트를 작성한다.
- CI 필수 단계는 format check, lint, typecheck, unit test, integration test, production build다.
